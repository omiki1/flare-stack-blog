## 0. 核心事实：GitHub 现在没有连接 Cloudflare

首次部署是从本机用 `wrangler deploy` **直接推到 Cloudflare** 的。所以现在：

```text
你改代码 ──► git push ──► GitHub          ← 只是存档，存了版本
                             ╳ 断的
                      Cloudflare 上的网站  ← 不会变
```

**结论：改完代码必须在本机跑一条部署命令。** 想变成"推送即上线"，见第 5 节。

但**写文章、改设置不需要部署**（见第 1 节），因为那些是直接写进数据库的。

## 1. 写文章 / 改设置 —— 不需要任何部署

这是日常 90% 的操作，**完全不碰代码，也不需要 Git**。

### 操作步骤

1. 浏览器打开 <https://blog.omiki.cc>
2. 点右上角登录，用 GitHub 授权
3. 进入 `/admin`

### 后台能做什么

| 想做的事 | 位置 | 备注 |
| --- | --- | --- |
| 写 / 改文章 | 文章 → 编辑 → **点发布** | 见下面「最大的坑」 |
| 改站点名称、介绍、作者 | 设置 → 站点 | 立即生效 |
| 换头像、首页背景、主题色相 | 设置 → 站点 | 立即生效 |
| 改导航栏、社交链接 | 设置 → 站点 | 立即生效 |
| 上传图片 | 媒体 | 存入 R2，单文件上限 10 MB |
| 管理分类与标签 | 分类标签 | 改分类名会影响已发布文章的公开展示，**无需重新发布** |
| 审核友链申请 | 友链 | 申请人会收到邮件通知 |
| 禁言 / 解禁用户 | 禁言用户 | 或直接在评论上操作 |
| 配置通知邮件与 Webhook | 设置 → 通知 | |
| 签发 API Key | 设置 → API Keys | 见第 9 节 |
| 重建搜索索引 | 设置 → 维护 | 内容大批量变动后跑一次 |
| 清缓存 | 设置 → 维护 | |

### 最大的坑：改完文章必须重新「发布」

v2 的规则是：**发布时才更新"公开内容快照"，读者看到的是快照。**
自动保存和编辑稿的改动**不影响**访客看到的版本。

所以：

- 改了标题 / 正文 / 摘要 / 链接 → **必须重新点「发布」**
- 只改了**分类或标签归属** → 不需要重新发布
- 想撤销发布、让文章暂时消失 → 用「取消发布」

### 其他常见困惑

| 现象 | 原因与处理 |
| --- | --- |
| 搜不到刚发的文章 | 去「设置 → 维护 → 重建搜索索引」 |
| 删不掉某张图片 | 刻意的保护：只要编辑稿或已发布内容还引用它就不允许删。先从文章里移除引用 |
| 评论想先审核 | v2 起评论**提交后直接公开**，没有审核环节。不合适就删除，删除后保留占位以便继续对话 |
| 分类改名后文章列表没变 | 分类归属改动不需要重新发布，但公开缓存可能延迟，去「设置 → 维护」刷一次 |

## 2. 改主站 omiki.cc 的代码 —— 一条命令

主站是纯静态站，**没有数据库**，所以这条路径零风险。

### 日常流程

```powershell
cd C:\workspace\wuwa

npm run dev          # 本地预览 → http://127.0.0.1:3000
                     # 改完看效果，Ctrl+C 停止

npm run check        # ESLint + TypeScript 检查（必须，别跳过）
npm run verify       # 构建 + 导出结构检查

npm run deploy:cf    # ★ 部署上线，约 1 分钟
```

### 可用的 npm 脚本

| 命令 | 作用 |
| --- | --- |
| `npm run dev` | 本地开发服务器 |
| `npm run build` | 只构建，导出静态站到 `out/` |
| `npm run check` | ESLint + 类型检查 |
| `npm run verify` | 构建 + 导出结构校验 |
| **`npm run deploy:cf`** | **构建 + 部署上线（日常用这条）** |
| `npm run deploy:cf:only` | 跳过构建，直接部署本地已有的 `out/` |
| `npm run deploy:doctor` | 只检查凭据是否就绪，不真正部署 |
| `npm run preview:cf` | 用 Worker 运行时本地预览 |

### 部署后怎么确认生效

浏览器打开 <https://omiki.cc> 刷新。看到旧内容就按 `Ctrl+Shift+R` 强刷。

## 3. 改博客 blog.omiki.cc 的代码 —— 先看警告

### ⚠️ 首先记住这一条

```bash
bun run deploy     # 等价于 bun db:migrate && wrangler deploy
```

**它每次都会先对生产数据库（D1）执行迁移。**

- 首次部署时库是空的，没风险
- **以后每次部署都会重复这个动作**

所以：**只要这次改动涉及 `migrations/` 目录，部署前必须先备份。**

### 日常流程（只改前端 / 文案，不动 migrations）

```powershell
cd C:\workspace\flare-stack-blog

bun install                 # 依赖有变动时才需要
bun run check               # orpc:contract + oxlint + oxfmt + 类型检查
bun run test                # 集成测试（16 文件 / 215 用例）
bun run test:node           # 单元测试（52 文件 / 258 用例）
bun dev                     # http://localhost:3000 人工走查

# 部署（需要 Cloudflare 凭据，见下）
$env:CLOUDFLARE_API_TOKEN = (Get-Content C:\Users\freeing1\.dsh-secrets\cloudflare.env |
  Where-Object { $_ -like 'CLOUDFLARE_API_TOKEN=*' }) -replace '^CLOUDFLARE_API_TOKEN=',''
bun run deploy
```

### 完整流程（涉及 migrations/）

```powershell
# 1. 先看清这次迁移要做什么 —— 有没有 DROP TABLE / DROP COLUMN / UPDATE
git diff HEAD -- migrations/

# 2. 【必须】备份生产 D1
bunx wrangler d1 export DB --remote --output "backup-$(Get-Date -Format 'yyyyMMdd-HHmmss').sql"

# 3. 先在本地库上跑一遍，确认不报错
bun run db:migrate:local

# 4. 本地起服务人工验证
bun dev

# 5. 确认无误再部署到生产
bun run deploy
```

### 备份文件放哪里

放到**仓库之外**的可靠位置（加密云盘 / 本地备份盘）。
**不要提交进 Git** —— 里面包含全部用户邮箱与评论内容。

### 部署后怎么确认

**直接从浏览器打开 <https://blog.omiki.cc>。**

看 Worker 实时日志：

```powershell
bunx wrangler tail omiki1-blog
```

> **注意：这台开发机无法用命令行访问 `blog.omiki.cc`。**
> 原因见第 8 节。**博客的验证请在浏览器里做。**

## 4. 同步上游新版本

博客项目来自上游 `du2333/flare-stack-blog`。

### 版本策略

**只跟随正式 Release，不要跟随上游 `main` 的最新提交。**

```text
检查上游 Release
      ↓
读 Breaking Changes（Releases 页面）
      ↓
【备份 D1】
      ↓
本地合并 + bun check + bun test
      ↓
本地库上试跑新迁移
      ↓
人工确认
      ↓
git push → 上线
```

### 完整命令

```powershell
cd C:\workspace\flare-stack-blog

# 0) 干净起步
git status                  # 必须干净
git checkout main

# 1) 取回上游，不动工作区
git fetch upstream --tags

# 2) 看有哪些新 Release
gh release list --repo du2333/flare-stack-blog --limit 10

# 3) 读目标版本的说明，重点看「升级」「不兼容」
gh release view v2.1.0 --repo du2333/flare-stack-blog

# 4) 【必须】备份生产 D1
bunx wrangler d1 export DB --remote --output "backup-before-v2.1.0.sql"

# 5) 检查新增迁移有没有破坏性操作
git diff --stat HEAD upstream/v2.1.0 -- migrations/
git diff HEAD upstream/v2.1.0 -- migrations/

# 6) 合并
git merge upstream/v2.1.0
#    有冲突 → 看 docs/FORK_CHANGES.md 第 3 节

# 7) 装依赖 + 质量门禁
bun install
bun run check
bun run test
bun run test:node

# 8) 本地先试新迁移
bun run db:migrate:local
bun dev

# 9) 确认后上线
git push origin main
```

### 合并时唯一会冲突的地方

**`package.json` 的 4 行脚本**（为了在 Windows 上能跑类型检查）：

```diff
-  "typecheck": "bun run orpc:contract && ./node_modules/typescript/bin/tsc --noEmit",
-  "check": "bun run orpc:contract && oxlint && oxfmt --check && ./node_modules/typescript/bin/tsc --noEmit",
+  "typecheck": "bun run orpc:contract && node scripts/typecheck.mjs --noEmit",
+  "check": "bun run orpc:contract && oxlint && oxfmt --check && node scripts/typecheck.mjs --noEmit",
```

**冲突解法固定：** 保留上游对 `scripts` 的其他所有改动，
只把 `typecheck` / `check` 两行换回 `node scripts/typecheck.mjs --noEmit`，
并确认 `typecheck:upstream` / `check:upstream` 仍在。

## 5. 推荐：接入 Workers Builds（push 即上线）

接入后流程简化成：

```text
改代码 → git push → GitHub → Cloudflare 自动构建并部署 → 上线
```

不用再记部署命令，手机改代码也能发布。

> **这一步只能你自己在 Cloudflare 控制台点**，因为需要授权 Cloudflare 访问你的 GitHub 账号。

### 5.1 主站 omiki.cc

1. 控制台 → **Compute → Workers & Pages → Create application → Continue with GitHub**
2. 授权后选择仓库 `omiki1/between-tides`
3. 填写：

   | 设置项 | 值 |
   | --- | --- |
   | Project name | `omiki1-home` ← **必须与 `wrangler.jsonc` 的 `name` 完全一致** |
   | Build command | `npm ci && npm run build` |
   | Deploy command | `npx wrangler deploy` |
   | Root directory | `/` |
   | Production branch | `main` |
   | Builds for non-production branches | 取消勾选 |

4. 点 **Deploy**。

主站**没有机密需要录入**，接上就能用。

### 5.2 博客 blog.omiki.cc

1. 同样入口，选择仓库 `omiki1/flare-stack-blog`
2. 填写：

   | 设置项 | 值 |
   | --- | --- |
   | Project name | `omiki1-blog` ← **必须与 `WORKER_NAME` 一致** |
   | Build command | `bun run wrangler:prepare && bun run build` |
   | Deploy command | `bun run deploy` |
   | Root directory | `/` |
   | Production branch | `main` |

3. 展开 **Advanced settings**，添加 6 个**构建变量**（这些不是机密）：

   ```
   WORKER_NAME       = omiki1-blog
   DOMAIN            = blog.omiki.cc
   D1_DATABASE_ID    = 4216488c-a345-4f7d-a387-ccbe9b846b84
   KV_NAMESPACE_ID   = 6a34cbc64ec04ead8e251fc4d3071e97
   BUCKET_NAME       = omiki1-blog-media
   QUEUE_NAME        = omiki1-blog-queue
   ```

   可选再加 `BUN_VERSION=1.4.2` 固定构建环境的 Bun 版本。

4. 点 **Deploy**。

> **运行时变量与 Secret 不需要再填。** 它们已经存在于 Worker 上，
> 而 `wrangler.jsonc` 里有 `keep_vars: true`，重新部署不会清掉它们。

### 5.3 接入后的新风险

迁移会在**每次 `git push` 时自动执行**：

- 好处：不会忘记跑迁移
- 风险：**没在本地验证过的迁移会直接打到生产库**

所以只要动了 `migrations/`，仍然要按第 3 节先在本地库上验证。

### 5.4 可选：给部署加一道门槛

博客仓库里已有 CI 工作流 `.github/workflows/ci.yml`（上游自带），
在 pull request 上跑 lint / 类型检查 / 测试。

想强制"推送前必须通过检查"：GitHub 仓库
**Settings → Branches → Add branch protection rule**，对 `main` 勾选
`Require status checks to pass`。

> **注意：** 主站仓库 `omiki1/between-tides` **还没有** CI 工作流。
> 需要的话照博客仓库那份写一份，命令换成 `npm ci` / `npm run check` / `npm run verify`。

## 6. 回滚

| 出问题的东西 | 怎么回滚 |
| --- | --- |
| 主站页面 | `git revert <提交>` → `git push` → `npm run deploy:cf` |
| 博客代码（数据库结构没变） | 控制台 → `omiki1-blog` → **Deployments → 找上一个正常版本 → Rollback** |
| 博客代码（数据库结构已变） | **必须恢复 D1 备份。** 代码回滚救不了已执行的迁移，见下 |
| 一篇文章的旧版本 | 后台 → 文章 → 编辑 → 历史版本 → 预览 → 恢复（恢复只改编辑稿，需再发布） |
| 站点设置改错了 | 后台重新改回来（系统配置有版本号，冲突时会拒绝写入而不是静默覆盖） |

### 最重要的一条

> **代码可以回滚，数据库不会跟着回滚。**
>
> `wrangler deploy` 回滚到上一个版本，D1 里的表和字段**仍是迁移之后的样子**。
> 一旦迁移里包含 `DROP TABLE` / `DROP COLUMN` / 数据转换，
> 回滚代码**无法**恢复数据。唯一能恢复的是**迁移之前的备份**。

### 从备份恢复

```powershell
# 0) 先给「现在」留一份，避免二次损失
bunx wrangler d1 export DB --remote --output "backup-before-restore.sql"

# 1) 灌回旧备份
bunx wrangler d1 execute DB --remote --file "backup-before-v2.1.0.sql"
```

更稳的办法是用 Cloudflare 内置的 Time Travel 回到迁移前的时间点：

```powershell
bunx wrangler d1 time-travel info DB --remote
bunx wrangler d1 time-travel restore DB --remote --timestamp <unix秒>
```

> Time Travel 是**兜底，不是备份策略**：保留窗口有限，且无法只恢复单张表。

### 恢复后必做

1. 后台「设置 → 维护 → 重建搜索索引」
2. 登录一次确认管理员权限还在
3. 抽查文章、评论、友链、媒体是否完整

## 8. 已知的环境问题

### 8.1 命令行无法访问 blog.omiki.cc（本机问题，不是站点问题）

**症状：**

```
curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed
```

**原因：** 本机 Clash（Mihomo）以 TUN 模式接管了全部流量
（默认路由指向 `198.18.0.2`），而它对 `omiki.cc` 的**子域**走了一条不通的代理链路。

**证据：** 对照组实验 —— 一个**根本不存在的**子域
`this-host-should-not-exist.omiki.cc` 的失败方式与 `blog.omiki.cc` **完全相同**，
而 apex `omiki.cc` 正常。

**结论：** 站点本身没问题。**博客的验证请在浏览器里做。**

**修法（可选）：** 在 Clash 规则里给 `omiki.cc` 及其子域加直连（DIRECT）规则。

### 8.2 Machine PATH 里有一条损坏条目

`ram Files\nodejs\` —— 这是 `C:\Program Files\nodejs` 被截断的结果。

**影响：** Git for Windows 的 sh 拿不到完整 PATH，
导致 husky 的钩子报 `bun: command not found`（已用 `~/.config/husky/init.sh` 绕过）。
这条很可能也是 Clash 规则匹配异常的根源。

**修法：** 系统属性 → 环境变量 → 在**系统变量**的 `Path` 里
把 `ram Files\nodejs\` 改成 `C:\Program Files\nodejs\`。

### 8.3 PowerShell 5.1 默认 TLS 版本过旧

**症状：** `Invoke-WebRequest` 访问 HTTPS 报「基础连接已经关闭」。

**修法：** 命令前加一行：

```powershell
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
```

### 8.4 husky 钩子需要 `~/.config/husky/init.sh`

文件内容：

```sh
export PATH="$HOME/.bun/bin:$PATH"
```

**这是机器级配置，不在仓库里**，换电脑时要重做。

## 9. 安全注意事项

### 9.1 API Key 等同于管理员密码

后台「设置 → API Keys」签发的 Key 会**完全冒充你的管理员会话**，
拥有你的全部内容管理权限（唯一限制是不能创建/撤销别的 API Key）。

所以：

- 按用途各签一个，命名清楚（例如 `codex-drafts`）
- 不用了就撤销
- **绝对不要提交进任何 Git 仓库**，也不要贴到聊天里

### 9.2 Cloudflare API Token 只放仓库外

部署用的 Token 存放在：

```
C:\Users\freeing1\.dsh-secrets\cloudflare.env
```

**不要**把 Token 写进 `.env` 或任何 `.env.*` 文件 ——
主站仓库有意提交 `.env.production`，那个文件里不能放任何秘密。

> ⚠️ **首次部署用的那个 Token 已经出现在聊天记录里，必须视为已泄露。**
> 请打开 <https://dash.cloudflare.com/profile/api-tokens>，
> 找到它并 **Roll** 或 **Delete**，需要时再建一个新的（权限最小化）。

### 9.3 站点数据库里的第一个用户是管理员

这条规则来自 `src/lib/auth/auth.server.ts`：

```ts
before: async (user) => {
  const existing = await db.query.user.findFirst({ columns: { id: true } });
  if (!existing) return { data: { ...user, role: "admin" } };
  return { data: user };
},
```

判断依据是「**user 表是否为空**」，不是邮箱白名单，v2 已移除 `ADMIN_EMAIL` 配置。

**含义：** 如果将来重置数据库，**第一个注册的人会成为管理员**。
所以清库之后必须立刻自己登录一次，再公开地址。

核对当前管理员：

```powershell
bunx wrangler d1 execute DB --remote --command "SELECT id, email, role FROM user ORDER BY created_at;"
```

目前**未启用**。建议在注册、登录、评论、友链申请上开启人机验证。

- Cloudflare 控制台 → **Turnstile** → Add site → 添加 `blog.omiki.cc`
- 得到 Site Key（公开）与 Secret Key（机密）
- Secret Key 写入 Worker 的运行时机密；Site Key 写入构建变量
  `VITE_TURNSTILE_SITE_KEY`（需要重新构建才生效）

服务端校验在 `src/lib/orpc/procedure.ts` 的 `turnstileMiddleware` 里执行，
**不是**只有前端验证。

### 9.5 主站 CSP 尚未启用

首页有 7 个内联脚本（2 个自写启动脚本 + 5 个 Next.js 水合数据流，
体积随内容变化），另有 35 处内联 `style` 属性。

- 用 `unsafe-inline` → 几乎完全废掉 `script-src` 的防护意义
- 用 sha256 哈希 → 需每次构建重算，一旦不同步会让**整站 JS 被拦**（页面白屏）

所以正确做法是分两步：先上线其余安全头（**已完成**），
之后加一个构建后脚本生成哈希，再在真实浏览器里逐页验证。

完整说明与模板写在 `C:\workspace\wuwa\public\_headers` 的注释里。
